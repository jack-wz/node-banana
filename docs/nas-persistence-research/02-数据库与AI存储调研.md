## 0. 需求锚点（来自代码图谱结论）

node-banana 上 NAS 后要持久化的数据有四类：

1. **结构化元数据**：工作流定义、生成记录（提示词、模型、参数、成本、时间）、标签；
2. **大文件媒体**：图/视频/音频/3D（单体可达几十 MB，总量会持续增长）；
3. **语义检索**：按提示词/内容找素材、找历史生成（"AI 化"的核心）；
4. **可视化界面**：5 人团队非程序员也能浏览/筛选/标注素材（类 Teable 表格）。

业界对「媒体类应用」的通行做法是 **DB 只存元数据 + 文件系统/对象存储存二进制**，绝不把视频塞进关系型数据库的 BLOB。后面的方案都按这个架构评估。

## A. AI 表格 / 无代码数据库（用户提到的「Teable 趋势」）

这类产品本质是「Postgres 之上的可视化表格式数据库 + AI 助手」，2025-2026 年开源社区热度最高的方向之一，正好同时满足「存数据」和「可视化」两个诉求。

| 产品 | 技术底座 | AI 能力 | 自部署 | 备注 |
|---|---|---|---|---|
| **Teable** | PostgreSQL + Next.js，AGPL-3.0，v2.x（2026 年 5 月发 v2.2.0），约 2 万 stars | AI 表格 Agent / AI 自动化 / 管理后台——**官方部署文档明确属 Enterprise 许可功能** | Docker AIO 单容器（amd64 官方验证，arm64 未测），内置或外部 PG 均可，附件支持本地挂载卷或 S3 插件，首次启动约 2 分钟，镜像约 1.5GB | 「Teable 趋势」主角；中文团队背景、中文文档好 |
| **NocoDB** | PG/MySQL/SQLite，Node，AGPL | NocoAI（字段级 AI、GPT 集成） | Docker 极简单，资源占用小 | GitHub star 最高的 Airtable 替代品，生态成熟 |
| **Baserow** | Django + PostgreSQL，MIT | AI 字段（需配置模型） | Docker，模块多略重 | UI 精致，插件体系 |
| **NocoBase** | Node + PG，插件式无代码平台 | 有 AI 员工/插件 | Docker | 更像「应用搭建平台」，学习曲线略高 |
| **Directus** | 包在任意 SQL 库外的数据平台 | 一般 | Docker | 强项是「接管已有数据库立刻给出漂亮的管理界面 + API」 |
| Airtable / 飞书多维表格 | 云端 SaaS | 强 | 不可自部署 | 数据出不了内网，不符合 NAS 目标 |

**趋势观察**：这一类产品的 2026 走向是「AI Agent 直接操作表格」——表格不再只是给人看的 UI，而是给 Agent 读写的工作内存。这与「吴越 AI 团队用提示词+素材构建数据仓库、供后续优化」的目标高度吻合。

> ⚠️ **许可注意（已核实）**：Teable 官方部署文档写明 *"The Enterprise license unlocks advanced features including AI automation, AI agent, admin console..."* ——即**自部署社区版的 AI Agent 能力受 Enterprise 许可限制**，免费自部署拿到的是表格+协作+API。AI 对话能力要么走其云版/企业授权，要么用社区版做可视化、AI 层自行实现（见评估文档第 7 节）。

## B. 通用数据库（基底选型）

| 候选 | 适合点 | 顾虑 |
|---|---|---|
| **PostgreSQL 16 + pgvector** | 一个容器同时解决「元数据 + 向量检索」；Teable/NocoDB/Directus/Supabase 全部以它为底座；docker 镜像成熟 | 需要一点 DBA 常识（备份用 pg_dump 或卷快照即可） |
| SQLite + Litestream | 零运维、单文件、Litestream 持续备份到对象存储 | 多容器/多服务并发写入弱；向量扩展（sqlite-vec）生态小于 pgvector |
| MySQL/MariaDB | 团队熟悉度可能高 | 向量/JSON 能力弱于 PG，AI 生态明显倾向 PG |
| MongoDB | 文档模型贴合 workflow JSON | NAS 上资源占用大；与 AI 表格生态不搭 |

**结论性观察**：2026 年「AI 应用默认数据库」事实上收敛到了 Postgres——pgvector、JSONB、全文检索三位一体，一个容器覆盖本项目 80% 需求。

## C. 向量 / AI 数据库（"AI 化存储"层）

| 候选 | 形态 | 特点 | 适配度 |
|---|---|---|---|
| **pgvector** | PG 扩展 | 与元数据同库，JOIN 查询「提示词+素材+向量」一把梭 | 5 人团队、万级~十万级向量完全够用，**首选** |
| LanceDB | 嵌入式/文件式 | 列存、天然为多模态（图/视频 embedding + 原文件路径）设计，S3/磁盘直存 | 很适合「多媒体语料库」场景，可作为第二阶段专用语义库 |
| Qdrant | 独立服务（Rust） | 单容器轻量、过滤强 | 需要多维护一个服务，收益不明显 |
| Milvus | 独立集群 | 面向亿级向量 | 对 5 人团队严重过剩 |
| Chroma | 嵌入式/服务 | 原型快 | 生产持久化口碑一般 |
| Weaviate | 独立服务（Go） | 自带向量化模块 | 功能全但偏重 |

**AI 存储的新趋势（2026）**：

- **Agent 可读写数据库**：数据库通过 MCP / API 直接暴露给 AI Agent（Postgres MCP、各家 DB 的 MCP server），让「提示词优化 Agent」能自己查询历史生成数据；
- **混合检索**：向量 + BM25 全文 + 元数据过滤三合一成为标配（pgvector + PG 全文检索即可实现）；
- **Agent Memory**：Mem0 之类的「记忆层」把偏好/反馈存成可检索记忆，可用于沉淀团队对生成结果的评价；也出现了面向 Agent 的嵌入式记忆库（如 agentDB：Rust 嵌入式 + 向量检索 + 自带 MCP server），适合作为「Agent 工作内存」；
- **Agent 负载驱动 SQLite 复兴**：Turso 等推动「每个 Agent 一个库」的并发写 SQLite 路线，说明轻量嵌入式库在 Agent 场景仍有生命力（PocketBase 同属此思路）；
- **AI 表格即知识库**：Teable 等把「数据库行」直接变成 AI 可操作的实体，业务人员用自然语言维护数据。

## D. 文件 / 对象存储（媒体二进制层）

| 候选 | 说明 | 适配度 |
|---|---|---|
| **NAS 文件卷直存**（现状延续） | node-banana 已有的 save-generation 就是写文件；挂一个飞牛存储卷即可，SMB/WebDAV 天然可被团队其他工具访问 | 最省事，DB 里存相对路径 |
| **MinIO**（S3 兼容，单容器） | 给媒体加 S3 API，Teable 的附件存储、LanceDB、备份工具都认 S3 | 需要 S3 生态时再加，第二阶段候选 |
| SeaweedFS | 海量小文件更优 | 当前规模用不上 |
| 飞牛相册/原生应用 | 媒体浏览体验好 | 与 node-banana 元数据联动弱，仅作补充 |

## E. 云端 / 一体化选项（备查）

| 候选 | 说明 |
|---|---|
| Supabase（云端或自托管） | PG + Auth + Storage + 向量全家桶；自托管 docker compose 服务较多（10+ 容器），NAS 上偏重；云端版数据不在本地 |
| Neon / Turso | 云端 Serverless PG / SQLite，适合云上 Agent 场景，不符合「落在飞牛本地」目标 |
| **PocketBase** | 单 Go 二进制 + SQLite + 文件存储 + 管理 UI + 实时 API，极轻 | 若要「最省事的带 UI 数据库」是强候选；但向量与 AI 生态弱于 PG 系 |

## F. 可视化展示方式（横向汇总）

1. **类 Teable 表格 UI**（Teable/NocoDB/Baserow/Directus 直接连库）：浏览、筛选、看板/画廊视图、附件预览，非技术人员友好——与需求 4 完全对应；
2. **BI 仪表盘**（Metabase/Grafana 连同一个 PG）：生成量、成本、模型分布统计；
3. **node-banana 自身 UI**：GlobalImageHistory 等已有雏形，可改成读库；
4. **AI 对话式查询**：Teable AI Agent 或经 MCP 让 Codex/其他 Agent 直接答「上周用 XX 提示词生成的图哪些评分最高」。
